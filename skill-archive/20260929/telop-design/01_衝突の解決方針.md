# 衝突の解決方針

この文書は、要件書と現行の共通スキル整理版がぶつかる4点だけを扱う。いずれも、今回の作業で現行ファイルを変更するものではない。未実装の設計を、現行の動作と取り違えない。

## 1. 字幕位置

### 要件書との衝突

要件書は、テロップ生成側では位置を固定せず、Editing AIが映像を見て位置を決めるとしている。一方、現行の `out/common/04_工程_rough-edit.md` は、ChatCutで全製品共通の標準位置を使う。

### 解決方針

- Phase 1は、現行の固定位置を標準として使う。
- Telop Generation AIの出力には最終位置を入れない。
- Phase 1のRendererプレビューや透明素材で位置が必要な場合は、現行標準を既定値として渡す。既定値の具体値は現行のrough-edit文書を参照し、この設計書で重複管理しない。
- Phase 2でEditing AIによる位置決めを導入する。商品、人物、顔、手元、重要UI、TikTok UIなどを避けて位置を決める。
- Phase 2でEditing AIが位置を出すようになった時点で、固定位置は「Editing AIがいないときの既定値」に格下げする。

### 現行記述の扱い

現行のrough-editにある字幕位置、`caption_preset(product-video-center)`、字幕配置の順番はPhase 1ではそのまま残す。要件書の位置決めを理由に、現行ChatCut手順を先に書き換えない。

## 2. 字幕工程の位置

### 要件書との衝突

現行のrough-editは、`edit-plan.json`を実行するだけで、テロップ本文を書き換えない。要件書は、Telop Generation AIが見た目を決める工程を追加する。

### 解決方針

- ROUGH_EDITの前に、Telop Generation AIによる設計段階を追加する。
- この段階は、承認済みのセリフと意味メタデータを読み、テロップ種別、強調、フォント、色、縁取り、絵文字、モーションをTelop JSONにする。
- Telop Generation AIは開始・終了時間と最終位置を決めない。時間・位置は、要件書とPhaseの範囲に応じて既存の編集計画またはEditing AIが持つ。
- ROUGH_EDITは引き続き実行のみとし、セリフやTelop JSONの内容をその場で書き換えない。将来の有効化後は、Telop JSONを実行対象に加える。
- 現行の `SCRIPT LINE == NARRATION == TELOP` と、`telop_only` の既存分岐は維持する。新しい視覚指定は本文を書き換えるためのものではない。

新しい段階を独立した工程として置くか、ASSEMBLYの中に置くかはまだ確定しない。両案と推奨は `05_確認事項.md` に置く。

### 現行記述の扱い

`out/common/04_工程_rough-edit.md` の「planを実行するだけ」「テロップを書き換えない」は有効なままにする。新工程はrough-editの前に設計結果を用意するだけで、rough-editの判断を増やすものではない。

## 3. Gemini台本テンプレートの追記

### 要件書との衝突

要件書は、Gemini台本プロンプトの末尾に、役割・意図・感情・重要度・強調候補・映像ヒントと、6点の禁止事項を追加する。一方、現行の `03_共通_Gemini台本テンプレ.md` には固定の穴埋め記号、出力形式、台本検査との前提がある。

### 解決方針

- 既存プロンプト本体は変更しない。
- 追記は末尾だけに置く。既存の指示の途中へ割り込ませたり、既存の出力形式を置き換えたりしない。
- 追記する6項目は、役割、意図、感情、重要度、強調候補、映像ヒントとする。
- 追記する禁止事項は、セリフ本文に絵文字を入れない、フォントを決めない、色を決めない、モーションを決めない、テロップ位置を決めない、改行位置を決めない、の6点とする。
- これは設計段階であり、コード側の出力解析と検査が対応するまでGeminiへ送らない。
- 有効化後も、台本本文はナレーションと画面本文の正本であり、メタデータは別項目として保存する。

### 現行記述の扱い

現行の固定文字列、穴埋め記号、案の表示、根拠確認は維持する。メタデータを付けた場合に、本文の検査やナレーション生成がメタデータまでセリフとして扱わないことをコードで検証してから有効化する。必要なコード側変更は `04_Phase1最小実装計画.md` に列挙する。

## 4. ChatCutと独自Rendererの境界

### 要件書との衝突

要件書の目標形は、Telop JSONを独自Rendererで描き、透明背景のテロップ素材としてChatCutへ渡す形である。一方、現行のrough-editはChatCutの字幕プリセットと字幕配置を使っている。

### 解決方針

- Phase 1は、Telop JSONの生成、プレビュー、透明素材のレンダリングまでに限定する。
- Phase 1のChatCut連携は実装しない。現行のChatCut字幕プリセットと標準位置は、その間も現行のまま残す。
- Phase 2で、`Telop JSON → 独自Renderer → 透明背景テロップ素材 → ChatCut` の受け渡しを追加する。
- 独自Rendererがフォント、色、縁取り、絵文字、モーション、改行を描く。ChatCutは意味やデザインを決めず、音声・映像・透明素材をタイムラインに置く。
- 将来ChatCutをPremiere、DaVinci、FFmpeg、独自編集エンジンへ替えても、Telop JSONとRendererの出力を再利用できる境界にする。

### 現行記述の扱い

Phase 1では現行rough-editを変更しない。Phase 2で透明素材を使う場合も、既存のChatCut手順をいきなり削除せず、切り替え条件、失敗時の戻し方、字幕トラックを残すかを別途確認する。ここは `05_確認事項.md` に保留する。

## 4件に共通する適用範囲

今回の設計書は、現行スキルを自動で有効化しない。既存の司令塔の受理条件、配置ゲート、失敗台帳は現行の正本を参照する。テロップ固有の新しい受理条件を追加する必要がある場合は、まず `05_確認事項.md` で案として確認し、合意後に別の変更として扱う。
