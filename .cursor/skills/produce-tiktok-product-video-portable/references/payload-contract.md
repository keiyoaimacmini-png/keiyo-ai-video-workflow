# Portable payload contract

Use strict payload schema v4 for future new-product work. `portable_setup.schema_version` is exactly `"4"`. Reject unknown fields, older-version payloads, and legacy aliases; never put a machine path, account ID, secret, or external-storage destination in the payload.

Require exactly one model-matched product settings file and exactly one manifest material with `kind: "product_video_settings"`. Register its exact safe relative path and SHA-256, then store a canonical `product_settings` receipt with `status`, exact model, manifest material ID, path, settings SHA-256, schema version, hash-bound `resolved_settings`, and its resolved-values SHA-256. The resolved projection contains the CTA, default voice, base/fallback speed range, uniform caption-template resource ID, and canonical final-cut catalog asset/range from that single source. Validation reads and hashes the actual file below the trusted project settings root, parses those fields, and compares them to the manifest and receipt; payload-internal self-attestation is insufficient. Preserve the settings catalog ID literally in `final_visual_policy.catalog_asset_id`. Its portable `asset_id` is the catalog ID itself if already valid under the portable asset schema; otherwise it is exactly `asset-` plus the lowercase catalog ID, so `A064` maps to `asset-a064`. The reusable policy also binds the same settings SHA-256 and the video's common narration speed. Missing, duplicate, ambiguous, malformed, model/path/SHA-mismatched, catalog/portable-ID-mismatched, or stale resolved settings are `HOLD_PRODUCT_VIDEO_SETTINGS`. Do not add machine-local settings paths to the portable payload. Freeze original text, punctuation, and caption line-break indices before TTS; schema v4 stores character count, estimated read-aloud seconds, selected source/range, and safe inspection location in the canonical `script_review_receipt`.

## Provenance and media

Each available company-authoritative manifest material records `material_id`, `sha256`, `access_status: "available"`, and `observed_product_models`. Product models match `^AN-[A-Z0-9]{4,6}$`. `product_model_provenance` closes over every such material with `status: "verified"`, exact material IDs/SHA-256s, and one observed model. A company-observation conflict is recorded as `status: "conflict"` and stops with `HOLD_MODEL_UNVERIFIED`.

Each cut has `media_requirements` with controlled `semantics`, exact `canonical_description`, structured `must_show`, and structured `must_not_show`. It has exactly one of:

- `matched_sidecar_receipt`: exact asset ID, sidecar SHA-256/path, `status: "verified"`, canonical requirements SHA-256, and `matched_fields: ["canonical_description", "semantics", "must_show", "must_not_show"]`.
- `additional_asset_required: true`: this blocks an approved edit.

Use the exact `semantics` keys (`subject`, `action`, `composition`, `product_visibility`, `text_visibility`) and their exact generated `canonical_description`; freeform media descriptions are invalid. `subject` is any non-empty observed-content string and must truthfully describe what is actually visible. Person, product, hand, vehicle, landscape, and weather are examples, not an allowlist. `action`, `composition`, `product_visibility`, and `text_visibility` remain controlled enums. Canonical cuts carry source/timeline ranges and editor fields. Script, captions, and TTS carry their cut timeline; captions/TTS also carry their editor fields.

`product_visibility` is `none|full|partial`. Use `none` only for a problem/setup cut whose verified source actually contains no product; it must not support or imply an unobserved product claim. Every `must_show[*].subject` is likewise a truthful non-empty observed-content string with no fixed allowlist. `must_show[*].visibility` remains `full|partial` because it describes how the required subject itself is visible, independently of product visibility.

`script`, `captions`, and present `tts` each close exactly over all cut IDs. The final script dialogue, caption text, and present TTS text exactly equal `下からチェック！`, including the full-width exclamation mark.

Every canonical user-visible caption, regardless of `narration_target`, maps to a distinct cut `source_asset_id` and a distinct portable-asset `media_sha256`; the video therefore changes to a different source asset when the caption changes. Reusing one asset ID or the same media SHA-256 under another ID/path is `HOLD_DISTINCT_ASSET_PER_CAPTION`. Changing source in/out, splitting, duplicating, looping, crop, speed, zoom, transition, or effect is not a distinct source. Ignore only a caption cut explicitly held with `additional_asset_required: true` and no source; existing approval logic already blocks its edit. The canonical final asset may continue only in its no-caption tail after the CTA.

Before edit approval, ordered, chronological, contiguous cuts and script records must visibly and factually complete `problem_or_hook -> product -> use_or_change -> result -> problem_resolution -> cta`. `problem_resolution` is the verified factual/media-supported explanation of how the observable result resolves the opening problem. Every script record carries one `narrative_role` and boolean `narration_target`; consecutive records may repeat a role, but the compressed role sequence is exactly those six stages. A hook-plus-CTA outline, a missing/reversed stage, overlapping/reordered cuts, or a stage without verified source support is `HOLD_SCRIPT_INCOMPLETE` or `HOLD_MEDIA_NOT_MATCHED`. Freeze wording, punctuation, and intended line breaks before TTS generation.

Narration is required unless the canonical `narration_policy` records `mode: "none"`, `scope: "video"`, `user_explicit: true`, and a non-empty user receipt; that exception applies to the whole named video and never propagates. Every cut has exactly one caption. Every `narration_target: true` script/caption pair has exactly one TTS record; a decorative pair may omit TTS only when both records explicitly set `narration_target: false`. Script and caption always start at the cut start and match after whitespace/intentional-line-break removal. Targeted TTS starts at the same cut start and matches the same wording; punctuation, omissions, paraphrases, combinations, and splits are not normalized away. A bulk Holiday Twist render may join those frozen lines with blank lines as generation input only. After download, insert measured silent scene-split gaps and split to one clip per narration-target cut. Payload `tts.text` for each cut remains the exact frozen line; do not add ellipses or extra spoken punctuation to Japanese generation input.

`voice_policy` is mandatory for required narration. Its default preset is exactly `CapCut official ホリデーツイスト`; any other preset requires `source: "user_override"`, `user_explicit: true`, and a non-empty receipt. Every TTS record matches the policy's preset, pitch, voice processing, and common speed. `narration_policy` has `timing_strategy`, `common_speed`, `overflow_cut_ids`, `overflow_reason`, and ordered `overflow_evidence`: `normal` requires `1.0x` and an empty evidence list; `common_tts_acceleration` records one all-target `applied_sufficient` step at `1.2x` through `1.5x`; `longer_verified_distinct_source` first records common acceleration as `applied_insufficient`, then a SHA-bound replacement whose historical prior asset resolves through `portable_handoff.assets`, whose prior media/sidecar hashes and range reproduce its evidence hash, whose ID and media SHA are absent from every current selected cut, and whose current replacement range is longer; `slow_video_and_caption` records those first two steps as insufficient, then a SHA-bound slowdown whose read-back speed is below `1.0x` and whose timeline duration equals source-range duration divided by speed. The selected source remains verified and distinct for each caption; a slowed source is never distinct for another caption. Missing, partial, unchanged-range, stale, or out-of-order evidence is invalid.

For every non-final narration-target cut, the source cut and its caption end at the narration end. `final_visual_policy` binds the last cut, canonical catalog ID, deterministic portable asset ID, exact source duration/range, mode (`full_source` or explicit `approved_long_range`), non-empty user approval receipt, `product_settings.settings_sha256`, and `narration_policy.common_speed`. Its catalog ID/range must exactly match `product_settings.resolved_settings`, and its portable ID must equal the deterministic mapping and the actual final cut source. These reuse-key fields prevent stale or misidentified final blocks after a settings or common-speed change. A full-source final uses `source_in: 0`, `source_out: source_duration`, speed `1.0`, and a timeline duration equal to the source range. An unavailable final asset uses explicit `status: "hold"`; it is never replaced or shortened by inference. The final visual remains at its approved long/full range even when its caption and narration end earlier, and its exact dialogue, caption, and present TTS remain `下からチェック！`.

The verified `product_info.product_model` remains mandatory for provenance, asset identity, project naming, and delivery naming, but it is omitted from the video itself by default. Reject the canonical model string in every `script.dialogue`, `captions.text`, and present `tts.text`. This video-visible rule does not remove the model from internal payload fields, portable filenames, CapCut project paths, or post metadata outside the video.

Each non-HOLD cut's `source_asset_id` must exactly equal its receipt asset ID. An `additional_asset_required` cut has no source asset/in/out fields. `manifest_ref` is ordered, duplicate-free, and exactly mirrors manifest ID/SHA order. Facts cite `material_refs` containing both a manifest ID and its exact SHA. Caption and present TTS ranges are contained within their corresponding cut. `post_set` is mandatory; QA has exactly the eight prescribed unique axes, maxima, and total.

Script, caption, and present TTS ranges are all contained within their cut. `facts_used.classification` is exactly `verified_fact`. QA metrics are exactly `watch_retention`, `comment_rate`, `save_rate`, `share_rate`, and `purchase_rate`, each `not_measured`. Manifest uses `source_location` only: either HTTPS or a safe relative path; `source_reference` is rejected.

## Caption presentation requirement

Every caption has `position: "center"`: horizontally centered and positioned in the central screen region, never accepted as a bottom-caption substitute. It carries a `template_requirement` object with a non-empty `provider` string. Official CapCut text templates, including キラキラ変身, are optional. Use the case editor's caption program (ChatCut Caption Cards or CapCut native captions) for viewer-facing captions. Do not use Motion Graphics as the caption layer. Those caption-program renderings are valid when they meet the visual-quality rule: centered, non-duplicated, fully inside the visible safe area, and prominent (heavy weight, thick dark stroke, contrast band). Do not invent or prefill a CapCut resource ID. Do not stop the edit, HOLD, or reject a timeline because an official CapCut template was not applied or read back.

Use one editor of record for the whole case. When that editor is CapCut Web, read back the official `https://www.capcut.com/` origin before the first mutation. When the host supplies a different editor adapter for this same case, use that editor for picture, captions, mute, and export, and do not claim a CapCut resource read-back. Do not mix two picture timelines. Official Holiday Twist may still be generated on CapCut Text to Speech and imported as audio when the editor of record cannot emit that preset; that sidecar is not a second case.

Timeline completion requires an automated actual-read-back reconciliation keyed by cut ID: source count equals caption count, narration-target caption count equals TTS count, IDs are unique, starts align, and all ranges remain inside their cuts. Payload closure alone is insufficient evidence of actual placement.

Final visual QA inspects the real player of the case editor at the visible start and final animation state and includes the complete outline, shadow, decoration, readability, and frame margins.

## TTS placement and completion evidence

Generation confirmation and credit deduction are not proof that audio was added. After each generation, read back the editable CapCut Web timeline and require the actual expected TTS clip on the expected cut/track with the intended text, voice preset, common speed, and exact range. Count narration-target captions and placed TTS clips and require one-to-one closure.

Completion requires a full real playback check for presence, volume, intelligibility, text match, clean starts/ends, overlap, duplication, truncation, and spill across source boundaries. If the active tool cannot hear or reliably judge playback, hold as `AWAITING_USER_AUDITORY_CONFIRMATION`; metadata, waveforms, or generation receipts alone do not make the video complete or export-ready.

Every cut, source, script, caption, and present TTS time range uses a non-bool int handled exactly or a finite float, with `0 <= start < end <= 86400`. Reject non-numbers, strings, nulls, NaN, infinity, negatives, zero-length, reversed ranges, and huge ints before containment checks.

## Integrity, optional compatibility routing, and portability

The validator computes `integrity.production_payload_sha256` and `integrity.visible_content_sha256`; it does not write them. The authorization subject includes a normalized projection of every gate's checkpoint, action list, count, and destination subjects; changing that plan invalidates every bound receipt. Exact checkpoint/action/count plans are validated even while a gate is pending or not applicable, so an attacker cannot add deletion, inflate a credit limit, or otherwise broaden a later approval and then rehash it. Approval adds only the mapped receipt and destination evidence. The validator normalizes only append-only export and Drive outcome fields, so validator-checked results may be recorded after approved actions without rebinding and without broadening authority. The three routine checkpoints use exact mapped receipts: `approval_gates.edit` uses `台本OK` only for `rough_visual_edit` and requires the canonical `script_review_receipt`; `credit` uses `粗編集OK` only for finishing and one first-attempt TTS/credit per disclosed narration target; `export` uses `完成・書き出しOK` only for one new export; `cloud` may share that final receipt only for exact upload plus read-back when canonical original-request and destination-scope subjects hash exactly and require a new file. `publish` and `send` accept only their exact separate action enums and each requires a canonical destination/recipient subject bound to the visible-content hash.

The `routing`, `openclaw_prohibition`, and `camee_tiktok_shop` fields are an optional compatibility extension, not part of the provider-neutral core. Omit all three when that integration is unused. When `routing` is present, both booleans remain mandatory and strict: an OpenClaw-bound payload requires a passed, checked-last prohibition receipt with `matched_rule_ids: []`; Camee Neo/OpenClaw also requires a verified `https://shop.tiktok.com/view/product/<numeric-id>` receipt with matching `product_id`, no userinfo, and no nonstandard port. Compatibility receipts without `routing` are rejected.

`created_at` is offset-aware. Its Asia/Tokyo date produces the editable cloud project path `Space/<model>/AI作成_<model>_<YYYY_MM_DD>` only; it is not export-date evidence. Before export, `delivery.export_status` is `"pending"` and `export_receipt` is absent. After the download completes, `delivery.export_status` is `"completed"` and `delivery.export_receipt` contains an offset-aware `exported_at`, `production_ordinal`, `completed_video_basename`, exact `file_extension`, matching video `mime_type`, and exact `completed_video_filename`.

The Asia/Tokyo date of `export_receipt.exported_at` renders as `YYYY_MMDD`; `production_ordinal` is an integer from 1 through 20 and renders as `①` through `⑳`; the completed-video basename is exactly `YYYY_MMDD_<model>_AI作成<ordinal>`. `prior_completed_exports` binds verified status/time strictly before the current export, exact date/model/scope, count, ordered `completed_exports`, and `ledger_snapshot_sha256`. Each prior record contains the exact sequential basename, an earlier offset-aware export time in the same JST scope, media SHA-256, and SHA-256 of that record's three safe fields. Count equals list length, the snapshot hash equals the canonical list hash, and `production_ordinal` equals count plus one. The first export uses count zero and an empty hashed list. Missing, fabricated-count, ambiguous, unordered, duplicate, future/equal-time, or scope/hash mismatch is `HOLD_PRODUCTION_ORDINAL_UNVERIFIED`. The payload never stores Drive IDs, paths, or URLs for this ledger. Example: a payload created on `2026-08-04` but actually exported on `2026-08-26` produces `2026_0826_AN-S182_AI作成①`. The file extension belongs to the exported file, not the basename.

If a user-approved external delivery targets a Drive root, locate exactly one immediate child folder titled with the verified model, reject an exact-name duplicate, and create a new file only. After upload, read back and match file ID, the exact current `completed_video_filename`, its matching MIME type, byte size, and parent folder ID at or after the export time. Schema v4 keeps raw Drive IDs, URLs, and account details outside the portable payload; its append-only `drive_receipt` stores hashes of the file ID and approved parent scope plus exact safe metadata, read-back time, and a canonical receipt hash.

Chrome session maintenance is operational evidence outside the portable payload. If the official CapCut Web session is logged out, select TikTok login and rely only on the TikTok session already signed in to Chrome or Chrome saved-credential autofill; never read, copy, log, or serialize credentials, tokens, cookies, account IDs, or session URLs. After login, reverify the official CapCut origin, signed-in editor, and exact intended new project before mutation. Ambiguous account selection, failed autofill/session reuse, CAPTCHA, 2FA, recovery, new consent, or another user decision is `HOLD_CAPCUT_LOGIN_USER_ACTION_REQUIRED`. Gemini Web script draft uses the same Chrome-session rule at `https://gemini.google.com/`; the matching login handoff is `HOLD_GEMINI_LOGIN_USER_ACTION_REQUIRED`. Do not store Gemini chat URLs, account identifiers, or API keys in the payload.

Maintain an internal task-owned tab set for the current video. Only after Drive upload has the required exact read-back may the workflow close those task-owned CapCut, TikTok-login, and Drive Chrome tabs, then verify their absence. This close is covered by the standing workflow instruction and does not create a fourth routine checkpoint. Never close unrelated tabs or a mixed-use window, sign out, clear browsing data/saved passwords, or serialize tab/account/session identifiers. Uncertain tab ownership is `HOLD_TASK_TAB_IDENTITY_UNVERIFIED`; leave those tabs open. After verified Drive read-back that HOLD does not block `COMPLETE`. Unverified or unrequested Drive storage does not trigger the close.

Portable assets include stable ID, media/sidecar SHA-256, safe POSIX relative paths, and classification flags (`original`, `editable_project_dependency`, `shared`, `uncertain`).

`cleanup_preflight` is preflight-only and has no path, execute, delete, or unknown field. Candidates cross-check a known asset by ID/media SHA and must be hash-verified local working downloads that are not original, dependency, shared, or uncertain.

After `COMPLETE` and verified destination storage, local working-media deletion is an operational purge outside this payload. It uses `scripts/purge_local_working_media.py` and never deletes originals, Drive stored objects, receipts, or the sole remaining completed video.

The canonical payload also carries `goal_axis`, patterns, facts, hypotheses, audio, post set, eight-axis design QA, risk register, manifest closure, component hashes, and portable setup instructions. Each nested object is allowlisted; component hashes are validator-recomputed.
